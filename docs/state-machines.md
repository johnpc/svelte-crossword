# State machines

Every mode, phase or status in the app is listed here with the ONE file that
writes it. Components send events and derive what they render; they never
flip a status flag themselves. `scripts/check-state-machines.js` (part of
`./scripts/quality.sh` and CI) keeps this page honest: each row's owner must
exist and carry an `@state-machine <id>` marker, every marker in `src/` must
have a row here, and two retired patterns are banned for good — reading a
Svelte component's internals (`$$.ctx`) and side effects inside markup
(`{void …}`).

Rule of thumb: **one mode, one owner**. If you need a new boolean to describe
"which situation are we in", you need a new variant on an existing machine or
a new row below — not a flag.

## What changed on 2026-11-16 (and why)

The survey found these implicit machines; all were converted this round.

- **Puzzle lifecycle** (`src/routes/Puzzle.svelte`) was `clues.length === 0` + `outOfPuzzles` + `isPuzzleComplete` + a child binding `crosswordComplete` + three `used*` booleans + a timer with its own `isComplete` callback. The two completion flags had a documented race (the child binding stays `true` for one flush after a new puzzle loads, so a bogus 0-second completion could be recorded). Now `puzzle-session`: the store is the only writer, `gridSolved` is ignored outside `playing`, the completion is recorded in the `playing → solved` transition exactly once, and a failed load is a visible `error` phase with a **Try again** button instead of a spinner that never ends.
- **Preview lifecycle** (`src/routes/preview/PuzzlePreview.svelte`) detected completion by polling the engine component's private `$$.ctx` once a second to find its cells array, and revealed the grid through `{void onReveal()}` in the template. Both are gone: the preview is a `puzzle-session` driven by the engine's `bind:isComplete`, and a grid that should open solved is told so via the `revealed` prop. The former `puzzleStore.completedPreview` flag is the `solved` phase of `preview-session`.
- **Engine tool mode** (`Crossword.svelte`) was `isRevealing` + `isChecking` + a `revealTimeout` that could both be true and whose timer could end a reveal that had already been cleared. Now one `ToolMode` with a guarded timer; `processToolbarAction` is a pure reducer returning a `ToolbarEffect`.
- **Login screens** were `state` + `confirm` + `confirmForgotPassword`; a stale `confirm` could follow the user between screens. Now `auth-flow`, with the code step nested inside its screen.
- **Page loads** (history, history detail, leaderboard) were `isLoading` next to possibly-stale arrays; failures either toasted into an empty list or left a spinner forever. Now `RemoteData` with a visible failure message.
- **Reducer actions** were `{ type: string } & Record<string, unknown>`; now total discriminated unions (`PuzzleAction`, `KeydownAction`), so an unhandled action is a type error.
- **Toolbar duplication**: the preview had a copy of the toolbar markup; both now render `PuzzleToolbar` (preview hides History).

## Known gaps (documented, not hidden)

- `undo-history` keeps two parallel arrays (`cellsHistory`, `focusedCellIndexHistory`) with their own indices, and focus history is pushed on focus changes rather than on cell edits, so an undo restores the cell values exactly but the cursor only approximately. Behaviour is unchanged from before; a single history of `{ cells, focusedCellIndex }` snapshots would fix it.
- **Auth session** (signed in / anonymous) is not a shared machine: each page asks `getCurrentUser()` on mount and redirects. It works because every page does the same thing; a shared `authSession` store would remove the per-page boilerplate.
- `preview-session` lives in module memory (as the flag it replaced did): a full reload starts the preview over; SvelteKit client-side navigation keeps it.
